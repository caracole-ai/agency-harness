    01La thèse en trois rôles

    Tout ce qui suit découle d'un seul partage. Ce qui est testable est du code. Ce que le code ne sait pas faire est confié au modèle, à des étapes fixes. Ce qui engage l'entreprise est signé par un humain.

    Le code conduit
    Le moteurCalendrier juridique, couche sémantique, interdits, machine à états, journal, compteur de coût. Il enchaîne les étapes et décide des sorties. Aucun modèle dedans.
    Le modèle lit et écrit
    Aux bordsDeux rôles de fond : extraire (« Karim se désiste ce soir » → agent, vacation, date, avec extrait et doute) et rédiger (la proposition pour l'humain). Deux rôles de tri bon marché, classer et douter, qui ne rendent jamais qu'un « à vérifier ». Il ne choisit jamais l'étape suivante.
    L'humain engage
    L'approbationRien ne sort sans un oui : pas d'envoi, d'affectation, de signature. Le oui produit un jeton, et l'écriture exige ce jeton comme paramètre. Sans jeton, l'écriture n'existe pas.

    02Les règles du client se trient en trois tas

    Premier geste de tout projet. Chaque règle de la fiche métier va dans un tas selon sa nature, et le tas décide de sa forme technique.

    La bêtise classique est de mettre les trois dans un prompt : un interdit dans un prompt est une probabilité, un interdit en code est un fait.

    03Le schéma global

    Les outils du client restent en place, en bas. Le harnais les enveloppe. Le modèle est à côté du moteur, pas dedans. L'humain tient la seule clé qui ouvre l'écriture.

    04Le flux sur un cas réel

    Société de sécurité privée, 17 h. Un agent se désiste pour la vacation de nuit. Ce que fait le système, étape par étape, et l'état de la demande à chaque fois.

    1. Le message arrivePar WhatsApp : « Karim se désiste ce soir ». Filtre en code d'abord (expéditeur connu, mots-clés). Puis le modèle extrait : agent = Karim, site = Z, vacation = ce soir. Chaque champ porte son extrait et son doute ; l'heure, non dite, est prise du planning et marquée « déduite ». La sortie est validée par un schéma : hors schéma deux fois, la demande passe « à vérifier » et l'humain voit le message brut.
      état : reçue → extraite
    2. Le moteur calcule les candidatsPas le modèle. La couche sémantique répond à disponible(agent, vacation) pour chaque agent : carte valide à la date de la vacation (calendrier), repos minimal entre deux services (12 h ou 11 h, à trancher) sur la période glissante, pas déjà affecté. Il ne renvoie que des candidats valides, avec le motif d'exclusion des autres (« Marc : carte expirée le 12/10 »). Aucun candidat qualifié : il le dit, avec les trois plus proches et ce qui leur manque, et la demande est escaladée (E-02) vers la permanence — le responsable d'exploitation, ou l'astreinte la nuit. Jamais un candidat par défaut.
      état : candidats (ou escaladée)
    3. Le code classe, le modèle rédigeLes préférences sont des poids dans la config (connaît le site +3, distance −1/km) : le code trie. Le modèle écrit la proposition pour l'humain. Avant qu'elle parte, le contrôle pre-response repasse tous les interdits sur la proposition exacte (le modèle a pu mélanger deux noms) et vérifie le texte : aucun chiffre hors des données, aucune formulation interdite.
      état : proposée
    4. La délégation désigne qui décideRemplacement prévu au contrat du client : la permanence. Au-delà (nouveau site, renfort) : le gérant. La permanence reçoit : « Remplacer Karim par Sofiane ce soir, site Z. Carte valide jusqu'au 03/2027, repos 14 h, connaît le site. Oui / Non ». Pas de réponse avant l'échéance : rappel, puis le rôle suivant de la table. La vacation est à 21 h : la transition « trop tard » escalade avant l'heure, pas après.
      état : en attente d'approbation
    5. Le oui produit un jeton, le jeton ouvre l'écritureecrire_planning(affectation, jeton). Le moteur vérifie que le jeton correspond exactement à cette affectation, écrit avec l'identité d'écriture (droits minimaux chez le fournisseur), journalise : qui, quand, quelle règle, quelle source. Un non : la demande s'arrête, avec le motif, et le journal le garde.
      état : écrite (ou arrêtée avec motif)

    La même chose en machine à états

    Chaque flèche est une transition déclarée, chaque échec un état nommé. Rien ne « remonte » comme une exception.

    05Les contrôles, moment par moment

    Un contrôle est écrit une fois, avec une signature fixe, et monté à un moment du harnais. Aujourd'hui la machine à états l'appelle à la transition. Le jour où une tâche ouverte justifie qu'un modèle conduise, le même contrôle devient un hook sur l'appel d'outil, sans modification.

    C'est ce qui fait du moteur un harnais au sens strict, en réserve : on construit le harnais d'abord et on décide ensuite, tâche par tâche, qui on attelle dessus.

    Seul le code bloque, et il bloque fermé. Un contrôle qui rend refus est du code pur, testé par les T-xx de la fiche. Un contrôle qui plante ou expire refuse, jamais « laisse passer par défaut ». Un modèle (LLM, ou un classifieur comme Jev) dans un contrôle ne peut rendre que à vérifier.
    Structurel avant hook. Un hook intercepte une tentative ; une capacité absente n'a pas besoin d'être interceptée. Le modèle n'a pas d'outil « envoyer un mail », seulement « préparer un brouillon » : il ne peut pas envoyer, même si un hook a planté. L'écriture exige un jeton comme paramètre obligatoire. Le compte de lecture n'a pas le droit d'écrire, et ce droit est retiré chez le fournisseur. On n'intercepte que ce qui ne peut pas être retiré : le contenu d'un texte, la cohérence d'une proposition.

    06Les échecs, tous modélisés

    La densité d'une machine à états vient de ses branches d'échec, et elles sont toutes pareilles. On les écrit une fois dans le moteur ; chaque transition ne déclare que son chemin nominal et sa politique.

    Réessayer, bornéUn nombre de fois fixé, puis une autre sortie. Jamais sans fin.
    EscaladerVers un humain, avec ce qu'on sait : les candidats les plus proches et ce qui leur manque.
    S'arrêter avec motifLa demande reste en base, dans son état, reprenable. Le motif est au journal.
    Jamais réessayer sans fin
    Jamais deviner
    Jamais laisser tomber en silence
    L'échecCe que fait le moteur
    Un contrôle refuse (interdit, aucun candidat qualifié)Ce n'est pas un échec technique, c'est un résultat : escaladée (vers qui, la fiche le dit) ou arrêtée avec motif.
    Un outil tombe (connecteur en panne, délai dépassé)Réessais bornés, puis la demande reste dans son état, persistée, et l'agence est alertée. L'état est en base précisément pour reprendre là où on était.
    Le modèle rate (sortie hors schéma, refus, doute trop fort)Un réessai, puis « à vérifier » : l'humain voit le message brut et fait l'extraction lui-même. Le système n'a pas le droit de « faire au mieux ».
    L'humain ne répond pasVeiller tourné vers nous : rappel, puis le rôle suivant de la table de délégation. La question d'entretien « et quand cette personne est absente ? » sert ici.
    Le réel n'attend pas (la vacation est à 21 h)L'échéance est un champ de la demande ; une transition « trop tard » existe et escalade avant l'heure.

    07Contenir la complexité

    Le désistement est un cas simple et montre déjà une complexité réelle. Quatre manières de la tenir quand les processus seront plus denses.

    Une petite machine par archétype

    Veiller, Rapprocher, Planifier, Rédiger ont chacun cinq à huit états. Une tâche métier les enchaîne : désistement = Rapprocher → Planifier → approbation → écriture. On ne construit jamais la grosse machine « sécurité privée ». Au-delà d'une douzaine d'états, on coupe.

    La table est une donnée

    état × événement → état suivant, politique. Elle se lit, se diffe, se dessine automatiquement et se teste par scénarios, à des centaines. Si la hiérarchie devient nécessaire, le formalisme standard est le statechart (XState en TypeScript) ; on garde le format compatible dès le départ.

    La couche sémantique

    Entités (Agent, Vacation, Site, Carte) et notions dérivées (disponible, valide_a, delai_de_prevenance), chacune définie une fois en mots du client, avec sa source et ses tests. Le modèle ne calcule jamais une notion métier, il la demande. Les mots à double sens de l'entretien y trouvent leur définition ; une ambiguïté non tranchée repart en question au client. Maison et petit : une centaine de fonctions pures au-dessus des connecteurs de lecture, pas un produit de BI.

    La complexité est celle du métier

    Tout ce que fait la machine du désistement, la permanence le fait déjà de tête à 17 h. On ne l'ajoute pas, on l'écrit. Une table que le client peut lire et corriger vaut mieux qu'un prompt où la même complexité est cachée. Ce qui reste difficile : où couper entre archétypes, et tenir les tables à jour. D'où la fiche structurée.

    08Le coût d'inférence, contrainte de premier rang

    On vend à des TPE/PME : la facture de modèle ne doit pas gonfler feature après feature.

    La facture ne vient pas des deux appels par demande (quelques dizaines d'euros par mois à cinquante demandes par jour, moins encore avec le cache). Elle vient de trois choses qu'on refuse dès la conception : un agent en boucle, une relecture du contexte entier à chaque tour, et les features « on regarde tout ».

    Quatre conséquences, gravées. Chaque feature annonce son coût par unité (message, document, jour) et son plafond mensuel avant d'être construite. Le code d'abord. En cascade. Le moteur journalise chaque appel avec ses tokens et son coût ; le plafond par client est dans la config, validé au démarrage, et s'approcher du plafond est une alerte Veiller comme une autre.

    09Standard pour la plomberie, maison pour le produit

    Exclus, et pourquoi

    • RAG : nos données sont structurées, on les requête. Seul Chercher (avocats) en a besoin, et Attendu le fait déjà par construction, avec la citation exacte.
    • Essaims d'agents : plusieurs modèles qui se parlent multiplient les points où personne ne contrôle. Une demande = une machine à états.
    • Frameworks d'orchestration (LangChain et consorts) : ils cachent le flux de contrôle. Notre garantie est le flux de contrôle visible et testé.
    • Frameworks d'agent auto-améliorants (Hermes) : skills réécrites par l'agent, mémoire curée par lui, accès terminal central. L'inverse d'un interdit auditable.

    Trois étages, une seule source

    • Générique : moteur (calendrier, exécution des contrôles, machine à états, journal, approbation, cadre des connecteurs, compteur).
    • Par métier : la bibliothèque d'interdits de la fiche, la couche sémantique du métier, les archétypes activés.
    • Par client : config.yaml (seuils, rôles, poids, vocabulaire, plafond) et ses connecteurs. C'est ça, « sur mesure ».
    • La fiche métier structurée est la source unique : les vues terrain, la figure du site, la table de la machine et le code des contrôles en découlent. Deux listes de règles, c'est une règle appliquée que personne n'a vue.

    10Dans quel ordre fabriquer

    Le premier livrable ne contient aucun modèle. C'est voulu : c'est le moins risqué, le moins cher, et il est présent dans les quatre métiers.

    1. Connecteur de lectureDu planning, au début un export CSV suffit. Identité de lecture seule chez le fournisseur.
    2. Calendrier + couche sémantique + interdits + testsUn script qui lit le planning et dit ce qui cloche. C'est Veiller, livrable sans aucun modèle, et le premier pilote de chaque métier.
    3. Machine à états + délégation + approbationPar message, deux boutons. Le jeton. L'identité d'écriture, droits minimaux.
    4. Le modèle aux bordsExtraire et rédiger, sorties validées par schéma, journal des coûts, plafond. Évals sur des traces réelles : c'est le seul endroit où on en a besoin.
    5. Le solveurSeulement si le métier planifie (sécurité oui, avocats non).

    11À valider avant le plan

    1. Le partage code / modèle / humain tel que décrit en 01 et 02, y compris : le modèle ne choisit pas le remplaçant, le code classe.
    2. Les quatre moments et les trois verdicts (05), et la règle « seul le code bloque, fermé ».
    3. L'écriture : par l'identité d'écriture du moteur, verrouillée par le jeton (défaut), ou par le compte de l'humain qui approuve (plus fort, plus de friction). À choisir par client, ou une fois pour toutes ?
    4. Les trois sorties d'échec et la table des échecs (06).
    5. Une machine par archétype, table en donnée, XState seulement si nécessaire (07).
    6. La cascade de coût et le plafond par client dans la config (08).
    7. L'ordre de fabrication (10), Veiller en premier, sans modèle.
    8. Le langage et les briques nommées : TypeScript, zod, XState, SQLite (07, 09) sont une recommandation, pas une décision.
